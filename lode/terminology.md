# Terminology

- **Agent Skill** — a folder containing `SKILL.md` plus optional resources, loaded by a host when relevant.
- **SKILL.md** — the required entry file: YAML frontmatter plus instructions.
- **Canonical tree** — `.agents/skills`, the only real copy of every skill in this repository; it is not a required install location.
- **Skill group** — skills that share behavior under group-named central files, mirrored into each member and never linked to at runtime.
- **Group shared file** — the copy-ready `<group>-shared.md` central file; every member carries a byte-identical `references/<group>-shared.md`.
- **Repo-maintenance skill** — a skill that checks or changes this repository; it may name repo paths it checks, but still links only inside its own folder.
- **Progressive disclosure** — loading `name` and `description` at startup, the `SKILL.md` body on activation, and `references/`, `scripts/`, or `assets/` files only when the body names them.
- **Reference file** — a focused document under `references/` holding detail too dense for the body; named by `SKILL.md`, one level deep.
- **Skill size pass line** — the official recommendation for a `SKILL.md` body: under 500 lines and ~5,000 tokens; the catalog's ~200–300 line / ~3,000-token aim is advisory only.
- **Install copy** — one skill folder copied into a host's skills directory; it must work with no other file from this repository present.
- **Skill identity** — the folder name plus the `SKILL.md` inside it; the directory a host installs it into is never part of its identity.
- **Host** — an assistant or agent product that reads skills from disk.
- **Agent link** — a relative symlink to `../.agents/skills` placed where a host looks.
- **Wiring** — creating those links for a chosen set of hosts.
- **Default wiring** — `claude` plus `copilot`, the hosts that cannot rely on `.agents/skills`.
- **Opt-in host directory** — a native host directory created only when named or when `--all` is used.
- **Frontmatter** — the YAML block at the top of `SKILL.md`.
- **Description** — the frontmatter field hosts read before deciding to load a skill.
- **skills-ref** — the official reference validator from the Agent Skills project; it checks frontmatter and naming only.
- **Repo gate** — a skill that enforces this repository's catalog rules; `skill-verify` gates skills on top of the official `skills-ref` validator, and `agent-verify` gates agent and command files manually against the official host specs, because no validator exists for agent files.
- **AGENTS.md** — repository-agnostic agent instructions: how to work, git and privacy rules, verification, and documentation surfaces; it carries no project details.
- **Project guidance** — the repository-specific rules kept in `lode/`: layout, invariants, skills, scripts, commands, and validation.
- **README** — `README.md`, the high-level entry point for a repository visitor: what it is, what it contains, where to start.
- **Docs** — `docs/`, the human documentation tree, grouped by audience.
- **Docs audience** — one of `users/`, `operators/`, `developers/`, or `skills/` under `docs/`; each owns its detail, and other pages link to it.
- **Quickstart** — `docs/users/quickstart.md`, the from-scratch walkthrough: one fast, free path (install OpenCode, optionally add the OpenCode Browse extension so the run uses the existing signed-in browser session, pick a free model, point at a skill URL, ask it to install and use the skill). Surfaced first from `docs/README.md`; linked from the user guide, getting-skills, and the top-level README's Get started. Vendor commands there are dated like `browser-setup.md`. Two Mermaid boundary diagrams anchor the security picture: the request loop (only the typed request and task-page text leave the machine) after the three-part intro, and the browser-control reach map (task tabs / handed-back sign-ins and payments / what stays outside) after Step 2's trade-off bullets.
- **Lode** — `lode/`, this agent-owned memory and the home of project-specific guidance.
- **Protected account** — an X account that hides its posts until it approves a follow request.
- **Moot** — a person the user follows who follows back; a `twitter-moot-radar` source and one `twitter-compatibility` scope.
- **Associated account** — a moot, a following-only account, or a followers-only account; the default population `twitter-compatibility` scores when no account is named.
- **Focus account** — one or more accounts the user names for direct assessment; scored or researched whatever its relationship, with the category and moot overlap reported as context, never as a gate.
- **Compatibility scope** — `focus`, `moots`, `following-only`, `followers-only`, or `all`, chosen up front; it filters the population without changing the score formula.
- **Following-only** — an associated account the user follows that does not follow back.
- **Followers-only** — an associated account that follows the user without a follow back.
- **Category** — the per-target relationship label — `moot`, `following-only`, `followers-only`, or `not-associated` — shown with a score but never scored itself.
- **Multimodal evidence** — opt-in reading of images, video frames, and audio transcripts; text is the default, 0 subject points when off, lower-weight and capped when on, and never enough for high confidence alone.
- **Evidence mode** — `text` (default, always on), `images`, `video`, or `audio`; each extra mode is opted in by the user and capability-tested once per run.
- **Evidence gate** — the two checks before non-text evidence counts: the user opted into that mode, and it passed its capability test this run; a failed gate is reported `unavailable`, never a silent zero.
- **Capability test** — the per-mode proof that the host returns readable pixels or a transcript; failure marks that mode `unavailable`, keeps the run text-only, and is reported instead of a silent zero.
- **Visual area** — an interest area whose primary evidence may be images; image or frame matches count 2 and cap at 12 instead of 1 and 6.
- **Evidence unavailable** — the per-mode flag when the model or browser tool cannot return readable content for an opted-in mode; the run continues text-only.
- **Overlap** — the count of distinct moots following a candidate; it ranks a suggestion, never proves an interest.
- **Interest profile** — the user's named areas plus strictness, overlap bar, and exclusions; it gates and ranks suggestions.
- **Compatibility score** — a 0–100 weighted total over a bounded sample of two feeds under one frozen rubric; arithmetic on counted items, never a prediction.
- **Rubric** — the user's areas, signal terms, area weights, component weights, mode, and window; frozen per version, and a change makes earlier scores stale.
- **Signal lexicon** — the confirmed lowercase terms per area that mark a match; the compatibility score's measuring instrument.
- **Component score** — one of subject, conversation, format, voice, recency, or access, each a count-based 0–100 value.
- **Confidence** — `high`, `medium`, `low`, `insufficient`, or `unreadable`, derived from the items and tabs read; shown beside a score, never folded into it.
- **Source feed** — the signed-in user's own readable Posts, Replies, Media, and visible Likes, re-read every run.
- **Target feed** — the scored account's public Posts, Replies, Media, and visible reposts for the scoring window.
- **Bridge matrix** — the report table of interest areas by the top-scoring accounts.
- **Entry point** — the newest matching post within 14 days that asks a question or invites a reply, with a suggested angle; never a sent message.
- **Stale score** — a score older than 14 days or from a different rubric version; shown only as previous, never ranked.
- **Source set** — the moots whose Following lists surfaced a candidate; it grows while Following lists are read and is reused across interest changes.
- **Proof standard** — a quoted post or bio line with date and permalink, the moots behind it, and a live `Follow` control reading; no suggestion without it.
- **Near miss** — a high-overlap candidate without readable interest evidence, listed separately so the user can overrule the rubric.
- **Pending** — the control state after requesting to follow a protected account; a request, not a follow.
- **Settle window** — the period after a click before judging whether the UI changed: checkpoints through roughly 30 seconds, then re-reads near 60 and 120 seconds, because a flip can land near two minutes.
- **Unreadable** — a page that rendered a notice instead of a profile, such as a sensitive-content interstitial; recorded as a verdict with a reason, never inferred from.
- **Follow-up pass** — the start-of-run check of due pending requests and unverified clicks.
- **Run state file** — per-account local JSON at `~/.x-<skill>/` holding the criteria or interests in force, cursor, queue, verdicts, and follow-ups; it persists between runs and is the only place a real handle or private detail is written. When writing is refused or unavailable, the same structure is held in session state and printed for the user to verify, and the next run starts fresh.
- **State line** — the one- or two-line start-of-run summary of the state file path and what it currently holds; with no file, it names the path and says the run starts fresh, or session-only when writing is unavailable.
- **Persistence fallback** — continuing a state-writing run on in-memory session state when file write is refused or unavailable, printing it for the user to verify, and accepting that the next run starts fresh and may repeat work.
- **Linked evidence** — a handle, quote, or date in a run's output that opens the X profile or post it came from; only pages read in that run are linked, never a guessed URL.
- **Access failure** — a browser, network, or site condition that stops a page or control from rendering; a run-level stop and flag, never a verdict about the account.
- **Browser preflight** — the start-of-run proof of browser control, and when control is missing, the shared setup-guidance flow: say what is missing, ask one question on guidance depth (step by step, short version, or self-setup), name the environment, guide only from official vendor documentation read that run, first-party options first, the user's yes for every machine change, login handed to the user, and a passed control proof before the run continues. Authored once in `twitter-shared.md`; principles only — vendor commands, URLs, and product names never enter a skill, because they move; dated examples live only on `docs/skills/browser-setup.md` and `docs/users/browser-setup.md`.
- **Injected row** — an ad (a promoted post or account) or a suggestion module ("Who to follow", "You might like", "Discover more") that X interleaves into a feed, profile tab, list, or post page; never the account's content: not sampled, counted, quoted, queued, or acted on, and neither a content row nor an empty scroll stop. Operative rule authored once in `twitter-shared.md`.
- **Placeholder handle** — a fictional handle in skill text, docs, and examples, using the `@example_<name>` scheme (`@example_alice`, `@example_bob`, …) or `@moot_a`/`@moot_b` for moot slots, so every example is format-valid and unlikely to collide with a real account; structural tokens (`@me`, `@cand`, `@handle`, `@last_row_seen`) are not person placeholders. Real handles exist only in the run state file or in session state printed for the user to verify.
- **Following audit** — the review `twitter-following-audit` runs over the user's Following list against the interests in force; its population is accounts the user follows, and a named handle is audited whatever its relationship.
- **Verdict** — the per-account suggestion of `twitter-following-audit`: `keep`, `unfollow`, `mute`, or `recheck`; a suggestion for the user to apply, never an action the run performs. Block is deliberately outside the set: block severs contact, which is a safety decision, not a curation choice.
- **Optimism rule** — the audit's burden of proof: keep needs no evidence, every negative verdict needs a quoted dated item or a counted dormancy fact, thin or unreadable evidence never lands a negative verdict, safety findings are flagged for the user instead of converted into a block suggestion, and every card leads with what the account gives you.
- **Tie** — a fact that tempers an audit verdict toward keeping the connection: moot, follows the user, replied to the user in the window, or a relationship the user named. A tie is a profile fact or the user's word, never inferred.
- **Reason tag** — the neutral, dated cause behind a non-keep verdict: `inactive`, `focus-moved`, `outside-interests`, `volume`, `repost-heavy`, or `disagreement` (user-named only). Never shown bare: wherever a verdict is shown, the tag carries its counted fact (silence span, match count, repost share, volume rate, or the user's word) inline; the full quote and permalink stay in the card. A keep carries a fit line instead; flags carry their own reason (bot/farm, scam, harassment, impersonation), not a verdict tag.
- **Safety flag** — the audit's separate track for accounts with quoted, dated, profile-level evidence of bot or follow-farm patterns, scams, harassment toward the user, or impersonation. A flag never carries a verdict and a verdict never carries a flag; the flag card names the user's options — block (severs contact and also unfollows), report where platform rules are implicated, or unfollow alone — decided by the user, never suggested as the audit's own verdict, never performed.
- **Active window** — the age of the newest post that still reads as active in `twitter-following-audit`; default 90 days.
- **Dormant window** — the silence beyond which an audit account reads as long-dormant; default 12 months.
- **Recheck** — the audit verdict that defers instead of acting: look again at the recheck gap (default 90 days) and record a dated follow-up.
- **Audit version** — `twitter-following-audit`'s frozen instrument: areas, terms, strictness, windows, and evidence modes. A change bumps it and marks every verdict stale; a scope or batch change does not.
- **Held handle** — an account the user excludes from an audit run entirely; it never receives a verdict, which is not the same as a keep.
- **Plain-language question** — a question a run puts to the user that stands alone: one decision, plain words, the reason for asking, what each answer changes, a concrete example where it helps, and a default or "none" path; internal labels are translated inline, never asked bare. Authored once in `twitter-shared.md` and copied verbatim into every X skill.
- **Observed example** — an example inside a question or a proposed brief, built from what the run has actually observed about this user — the signed-in profile's bio and pinned post, anything already read this run (a named account's profile, saved state), or the user's own words — and offered as a guess to confirm, never stated as fact. With nothing observed, the question names the kind of answer wanted instead of planting a fixed subject. Rule authored once in `twitter-shared.md`.
- **Human cadence** — jittered waits, scroll steps, pointer moves, and dwell times drawn from ranges so a run does not read as a fixed click rhythm.
- **X core contract** — [`docs/skills/twitter-core.md`](../docs/skills/twitter-core.md), the authoring home for rules shared by every browser-driven X skill; skill bodies mirror it and never link to it.
- **Personal scope** — the X group's positioning: every member serves a real person on their own personal X account; never engagement farming, marketing, or brand work. Stated in each description, body intro, and Safety section; words with the negative marketing or engagement flavor never describe the skills' own behavior (read/collect/scan, "secondhand", "selling"), while exclusion labels and disclaimers keep their standard names.

- **Software-documentation rules** — the authoring contract `software-documentation` applies to any project's docs: one audience per page, one home per fact, a central terminology guide, current-state-only currency, diagrams beside the owning page, plain portable markdown, and doc comments on public contracts only; the default `docs/` placement yields to an existing layout or the user's choice.

- **Deadpan reductive one-liner** — `deadpan-reductive-observation`'s output style: one concise, confident sentence that reduces a subject to an unexpectedly mundane, literal, or absurd description of what it effectively consists of; the humor is the accuracy of the reduction, never a labeled joke or punchline. Researched alternatives are requested, not default, and never invent facts.

- **Subagent definition** — a single markdown file with `name` (kebab-case, matching the file stem), `description` (what, when, not-for), and `tools` in `.zcode/agents/`; one real copy, aliased to `.agents/agents`, `.claude/agents`, and `.github/agents`; stock for a stated project shape, never a universal reviewer.
- **Slash command** — a markdown file in `.zcode/commands/` that invokes one agent or procedure, aliased beside the agents; it carries the fallback for runtimes without subagents: read the definition and execute the procedure directly.
- **Agent alias chain** — `.zcode/agents` → `.agents/agents` → `.github/agents`, with Claude Code served by the whole-directory `.claude → .agents` symlink (commands likewise); committed relative links recorded as mode `120000`, never replaced by copies; `scripts/link-skills.*` create and repair the `.claude` and skill links.
- **Placeholder .gitignore** — an empty tracked `.gitignore` that retains an otherwise-empty agent-support directory (`agents/`, `prompts/`, `.zcode/plans/`) in the remote; `.zcode/plans/` drafts are ignored around it.
